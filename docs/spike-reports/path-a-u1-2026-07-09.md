## 真实根因分析(最终,spike #10 后)

**不是单点 bug,是 LLM codegen 系统性偏差,fix_loop 不解决根本**:

- ✅ GLM-5.2 / Minimax 都能产完整工程结构(5 文件 + 合理 AscendC 代码)
- ✅ cannbot skill(add_example 内联)提供正确构建模板
- ✅ compile fix_loop 机制工作(3 轮真循环,stderr 进 context,messages 累积)
- ❌ **LLM 在 fix_loop 内仍引入新偏差**(第 2 轮 `ascendc_add_ops` 幻觉)
- **机制对,LLM 知识盲区是另一层 long-tail**

**fix_loop 限制**:给 LLM 完整 stderr + 之前 messages + code_result.files,LLM 仍编造不在 add_example 里的命令。fix_loop 是 compile 嵌入循环,但 LLM 创造性 vs 模板精确性是固有偏差,几轮收敛不够。

**正确收敛路径 = prompt/scaffold 改造**(spike #4-#10 反复暴露同一根因):
- prompt 强令:完整复制 add_example/CMakeLists.txt 全文,只允许微调 -j*/--soc
- scaffold 注入:LLM 只写 kernel/host,build.sh/CMakeLists.txt 用 add_example 原版
- 这两选项交用户,不在 U1 spike 范畴
