## 执行摘要

**定位**：支持三条用户旅程的算子迁移/开发运行时引擎。CUDA + Triton 迁移能力全部复用 cannbot 成熟 skill（cuda2ascend-simt 已用 29 算子验证、triton 5-skill 链成熟），**项目 100% 代码量在运行时编排层**（阶段机 + checkpoint + NPU 执行 + 验证 + 批量 + 决策）。

**关键事实**：
- 硬件 A5/950 = cuda2ascend-simt 官方验证硬件 → CUDA 迁移端到端可验证，无硬件风险
- 三条用户旅程共享后端，前端入口不同
- 单算子闭环是地基（P0），模型级批量是增强（P1）

**工作量**：单人 **10-14 周**，分两阶段：
- P0 单算子闭环（路径 B+C，4-6 周）：第 4-6 周即可用——给一个算子（迁移或新开发），跑通"解析→迁移/实现→编译→验证"，崩溃可恢复
- P1 模型级批量 + 增强（路径 A + 闭环修复，5-8 周）：profiling + 选择性决策 + 批量并行 + 30 卡调度

**架构原则**：**共享后端、三前端入口**——运行时后端统一，前端只是"识别入口类型 → 调对应 cannbot skill"的薄胶水层。

## 第二节：三条用户旅程（产品骨架）

三条路径**共享后端**（阶段机 + checkpoint + 验证 + NPU 执行），前端入口和前置环节不同：

### 路径 A：模型级选择性迁移（P1）

```
客户模型（含 N 个自定义 CUDA/Triton 算子）
  → [模型 profiling] 算子耗时占比 + 迁移难度预估
  → [人机决策] 用户勾选要迁的
  → [批量并行迁移] 选中算子并行，各自 checkpoint
  → [验证] 精度/性能对比 + 失败分类
```
- 最复杂（profiling + 决策 + 批量）
- 依赖路径 B 的单算子迁移能力

### 路径 B：单算子迁移（P0）

```
单个 CUDA/Triton 算子源码
  → [识别] 判定 CUDA / Triton + 选交付模式
  → [迁移] 调 cannbot cuda2ascend-simt / triton 5-skill 链
  → [编译验证] AscendC 编译 + UT/ST + 精度对比
  → [交付] ported-ops/<op>/ 工程
```
- 中等复杂度
- 是路径 A 批量的基础单元

### 路径 C：单算子新开发（P0）

```
算子需求描述（名称/shape/dtype/语义）
  → [设计] 调 cannbot ops-spec-gen + ascendc-tiling-design
  → [实现] 调 cannbot ascendc-api-best-practices 生成 kernel
  → [编译验证] 编译 + UT/ST + 精度对比
  → [交付] 算子工程
```
- 中等复杂度
- 占工作量 20%，但复用 cannbot 同一套 skill

**关键洞察**：路径 B 和 C 是地基，跑通后路径 A 自然是"profiling + 决策 + N 个路径 B 并行"。所以 **P0 聚焦 B+C，P1 叠加 A**。

## 第三节：架构原则——共享后端、三前端入口

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌──────────────┐
│路径A前端     │  │路径B前端     │  │路径C前端     │  │ 模型profiling │
│(批量编排+   │  │(单算子迁移:  │  │(单算子开发:  │  │ +决策前端     │
│ 决策,P1)    │  │ CUDA/Triton)│  │ spec→kernel)│  │ (P1)         │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘  └──────┬───────┘
       └────────────────┼────────────────┴────────────────┘
                        ▼
       ┌─────────────────────────────────────────┐
       │        共享运行时后端（本项目重点）        │
       │ - 阶段机 + checkpoint（崩溃恢复）          │
       │ - cannbot-skills 集成（阶段感知加载）      │
       │ - NPU 执行封装（P0轻量 / P1池调度）        │
       │ - 编译/UT/ST/精度/性能验证（统一）          │
       │ - 闭环修复（P1）                          │
       └─────────────────────────────────────────┘
```

**前端都是薄胶水**（~200-500 LOC 各），因为只是"识别入口 → 调 cannbot skill → 收集产物"。**所有代码量集中在共享后端**。

## 第四节：MVP 边界（Spike 0 + P0 + P1）

### Spike 0（集成验证，1 周）

CUDA 可行性已被华为验证（29 算子）+ 硬件是 A5/950（官方验证环境），Spike 0 只验证集成：

| 验证项 | 方法 | go 标准 |
|---|---|---|
| cannbot-skills 集成 | git submodule + PromptBuilder Layer 6 阶段感知加载 | Phase2 实际加载 ascendc-tiling-design |
| **cuda2ascend-simt 在 A5/950 跑通** | 选 1 个 CUDA sample（如 vectorAdd），skill 迁移 + 编译 + 验证 | 产出 Ascend C SIMT 工程，在 950 上 validation 通过 |
| **triton 链在 A5/950 跑通** | 选 1 个简单 Triton 算子，走 5-skill 链 | 产出 AscendC kernel + 编译通过 |
| 精度对比协议 | kernel 输出 vs numpy 基线的格式 + 容差 | 能算 abs_err/rel_err/cos_sim |

**go 标准**：两个迁移 skill + 一个开发 skill 都能在 A5/950 跑通端到端。

### P0（单算子闭环，路径 B+C，4-6 周）

目标：单个 CUDA/Triton 算子迁移、或单个新算子开发，跑通"解析→迁移/实现→编译→验证"，崩溃可恢复。

| 模块 | LOC | 说明 |
|---|---|---|
| **cannbot-skills 集成** | ~200-400 | git submodule + PromptBuilder Layer 6 阶段感知加载 |
| **阶段机 + checkpoint** | ~600-900 | LangGraph StateGraph，单算子崩溃恢复 |
| **路径B前端：单算子迁移** | ~400-700 | CUDA（调 cuda2ascend-simt）+ Triton（调 5-skill 链），含交付模式选择 |
| **路径C前端：单算子开发** | ~200-400 | 调 ops-spec-gen + ascendc-tiling-design + ascendc-api-best-practices |
| **统一验证后端** | ~400-600 | 编译 + UT/ST + 精度对比（numpy 基线）+ 性能 |
| **轻量 NPU 执行封装** | ~200-400 | 单算子用：cann_compile/msop/msoprof 统一接口，结果归档 |
| **合计 P0** | **~2000-3400** | 单人 4-6 周 |

**P0 验收**：
- 给一个 CUDA 算子 → 迁移到 AscendC SIMT，在 A5/950 编译 + 精度验证通过
- 给一个 Triton 算子 → 同上
- 给一个新算子需求 → 生成 AscendC kernel，编译 + 验证通过
- 三者都支持崩溃恢复

### P1（模型级批量 + 增强，路径 A + 闭环，5-8 周）

| 模块 | LOC | 说明 |
|---|---|---|
| **模型 profiling + 算子耗时占比** | ~600-1000 | 跑客户模型，算子级耗时分解 |
| **选择性决策前端** | ~400-700 | 耗时排行 + 迁移难度预估（用 cannbot 降级分类做信号）+ 用户勾选 |
| **批量并行编排** | ~800-1400 | 1-10 算子并行，各自 checkpoint，失败分类，部分恢复 |
| **NPU 池调度升级** | ~600-1000 | 30 卡：卡池状态、排队、共享/独占、失败重试（单租户多任务）|
| **闭环修复控制器** | ~300-500 | review→fix→re-review→stop，有界循环 |
| **合计 P1** | **~2700-4600** | 单人 5-8 周 |

### 明确不做（自用低价值）

| 模块 | 原因 |
|---|---|
| 重写 CUDA/Triton 迁移逻辑 | cannbot 已覆盖（A5/950 已验证）|
| 多租户隔离/计费/配额 | 单团队自用 |
| 结构化审计签名 | 自用不需合规 |
| CI/CD PR 自动化 | 自用本地开发 |
| 统一编译器 IR | 研究级，超范围 |

## 第五节：风险登记（纠正后）

CUDA 迁移和硬件适配风险均已消解。**真正风险在运行时编排层**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 30 卡池并发正确性（P1）| 卡状态表、共享/独占切换、失败重试的并发设计是新增代码 | 参考 hermes 的 ThreadPoolExecutor + IterationBudget；P1 专项测试 |
| 批量并行失败隔离（P1）| 1-10 算子并行，一个失败不能拖垮其他 | 每算子独立 checkpoint + 独立进程，失败归档不阻塞 |
| 选择性决策的难度预估准确性（P1）| 估错会误导用户 | 用 cannbot 降级分类（downgrade/blocked/excluded）做信号，初版保守 |
| 阶段机与现有 ReAct 循环集成 | 现有 AIAgent 是 145 行 ReAct，如何挂阶段机 | 按重构报告：阶段机作为外层，ReAct 作为 LLM 节点内部调用 |
| cannbot skill 版本耦合 | submodule 依赖华为维护 | skills 是 markdown+YAML 可 fork；运行时价值独立 |

**已消解风险**（追溯）：~~CUDA 迁移可行性~~（cannbot 29 算子验证）、~~硬件适配~~（A5/950 是官方验证环境）。

## 第六节：30 卡 NPU 池（P1，单租户多任务）

P0 单算子不需要复杂调度（轻量执行封装即可）。30 卡池调度是 P1 路径 A 批量并行的需求：

| 商业版多租户调度（不做） | 自用版单租户调度（P1 做）|
|---|---|
| 租户隔离、计费、配额、SLA | ❌ |
| — | ✅ 卡池状态表（空闲/占用）|
| — | ✅ 任务排队（FIFO + 优先级）|
| — | ✅ 共享/独占切换（profiling 独占，编译共享）|
| — | ✅ 失败检测（OOM/ECC/hang）+ 重试 |
| — | ✅ 结果归档（build hash + 基线对比）|

**LOC**：~600-1000（单租户简化版）
