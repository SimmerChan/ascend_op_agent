## 根因分析

**不是单纯 LLM kernel 写作能力问题** —— LLM 根本没尝试写 kernel(5 个 codegen 节点都回空占位)。两层根因:

### 层 1:LLM 行为(主要)
- 5 节点 codegen 的 prompt 要求"调用 file_write 工具写 1 个文件"(new_dev.py:233-237)
- GLM-5.2 实际行为:回 ~20 字符占位,唯一 tool_call 是 `shell_exec`
- 即 GLM-5.2 在该 prompt + OpenAI 协议下,tool calling 不按预期(file_write 未触发)

### 层 2:graph codegen 节点设计(需 U2 诊断)
- 5 个独立 LLM 节点各写 1 文件(make_llm_node,new_dev.py:204-246)
- codegen 节点 LLM 输出 20 字符占位 → 无 file_write → 无文件 → `code_result` 不被填充
- 可能子因(待 U2 查):
  - make_llm_node 是否截断 LLM response 到占位(聚合 bug)
  - GLM-5.2 OpenAI 端点 tool calling 兼容性
  - 5 节点 prompt 一次性期望 vs LLM 单轮能力

按 plan U1 规则:**pass_rate 0% < 50% → 触发"不分期"重开对话 → 停 U4/U8,回用户**。

不同于首跑误判,本次 NO-GO 是**真实信号**:在当前 graph + GLM-5.2 配置下,5 节点 codegen 路径无法产出可用文件。但根因是 **codegen 节点设计 + LLM tool calling 行为**,不是"LLM 不会写 AscendC kernel"(LLM 没机会尝试)。
