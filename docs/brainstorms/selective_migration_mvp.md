## 执行摘要

**场景确认后的 MVP 重定位**：从"通用算子开发内部工具"聚焦到**"性能驱动的选择性迁移引擎"**——客户模型 → profiling 出算子耗时占比 → 用户勾选要迁移的 → 并行迁移（30 卡池调度）→ 精度/性能验证。

**复杂度诚实评估**：你的场景（30 卡 + 迁移主导 + 批量 + **CUDA 占 50%**）**接近商业产品级**。单人工作量 **14-21 周**（约 3.5-5 个月），分三阶段：Spike 0（含 CUDA 可行性，2 周）→ P0 双轨（Triton + CUDA，6-9 周）→ P1 批量+闭环（6-10 周）。

**最大风险已前置**：CUDA→AscendC 迁移（cannbot 的 cuda2ascend-simt 是空桩，华为都没做好）。因为 CUDA 占 50%，**Spike 0 必须验证 CUDA 可行性**，结果决定 CUDA 路径是"全自动 / 半自动（LLM 草稿+人工修正）/ 不可行降级"。Triton 有 cannbot 成熟 5-skill 链，低风险。

**架构原则**：**共享后端、分前端**——迁移后端（AscendC 生成 + 验证 + 调度 + checkpoint）统一，前端分 Triton 解析（复用 cannbot）和 CUDA 解析（自建）。避免做两个独立引擎。

**产品差异化**：不是全自动迁移引擎，而是"性能驱动 + 人机协作的选择性迁移"——这比纯自动化更现实（不是所有自定义算子都值得迁）。

## 第一节：确认的场景

| 维度 | 确认值 | 对架构的含义 |
|---|---|---|
| NPU 卡数 | **>30 张**，可共享可独占 | NPU 资源池调度是 P0 基础设施；单租户多任务，砍多租户隔离/计费 |
| 迁移:新开发 | **8:2** | 迁移流水线是 P0 核心工作量 |

| 批量规模 | **1-10 个/次** | 批量控制器 P0，规模可控 |
| 迁移策略 | **选择性**（按耗时占比，用户决定）| 需要 profiling + 耗时分解 + 决策环节，这是产品核心特性 |
| 商业化 | 内部工具，不对外 | 砍审计签名、CI/CD、多租户（但保留 30 卡调度）|

## 第二节：核心用户旅程（产品骨架）

```
┌─────────────────────────────────────────────────────────────┐
│ 输入：客户提供模型（含 N 个自定义 CUDA/Triton 算子）          │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段 1：性能分析（NPU 池）                                    │
│ - 跑客户模型，profiling 每个自定义算子的耗时                  │
│ - 产出：算子耗时排行 + 占比表 + 迁移难度预估（Triton/CUDA 分类）│
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段 2：迁移决策（人机协作）                                  │
│ - 展示耗时占比 + 每个算子迁移难度/收益预估                    │
│ - 用户勾选要迁移的（如 top 5，或耗时 >5% 的）                 │
│ - 用户可选独占/共享卡模式                                     │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段 3：并行迁移执行（NPU 池调度，共享后端 + 分前端）          │
│ - 选中算子并行迁移，每个独立 checkpoint                       │
│ - Triton 算子 → cannbot 5-skill 链前端                       │
│ - CUDA 算子 → 自建前端（按 Spike 0 结果定自动化程度）          │
│ - 两者汇入统一后端：AscendC 生成 → 编译 → 验证                │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段 4：验证与交付                                            │
│ - 精度对比（vs 原算子输出）                                   │
│ - 性能对比（vs 原算子 + 迁移前后模型端到端）                   │
│ - 失败分类（tiling/precision/compile）+ 重试/人工介入          │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：阶段 2 的"人机协作决策"是这个产品的灵魂。不做全自动迁移，因为不是所有自定义算子值得迁（有些框架原生 op 替代更划算），迁移难度/收益需要人判断。

## 第三节：架构原则——共享后端、分前端

5:5 比例下，**不要做两个独立迁移引擎**。正确架构：

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ Triton 前端   │    │  CUDA 前端    │    │ 新算子前端    │
│ (复用cannbot │    │ (自建,Spike0 │    │ (复用cannbot │
│  5-skill链)  │    │  验证可行性)  │    │  ops-spec-gen)│
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │ 统一算子中间描述(OpSpec)        │
       └────────────┬───────────────────┘
                    ▼
       ┌────────────────────────────┐
       │     共享迁移后端（统一）      │
       │ - AscendC 代码生成           │
       │ - 阶段机 + checkpoint        │
       │ - 编译/UT/精度/性能验证       │
       │ - NPU 池调度                 │
       │ - 闭环修复                   │
       └────────────────────────────┘
```

**收益**：后端写一次，三前端复用。CUDA 难在前端解析（SMEM↔UB、tile 推断），后端的"生成 AscendC + 验证"逻辑与 Triton 共享。

**不追求统一 IR**：统一中间表示（如 Triton IR 或自研 IR）是编译器研究级难题，超出范围。务实做法是前端各自产出"半结构化算子描述（OpSpec：算子语义 + shape + dtype + 并行策略）"，后端据此生成 AscendC。

## 第四节：MVP 边界（Spike 0 + P0 + P1）

### Spike 0（风险验证，2 周）——开工前的 go/no-go

**核心目标：验证 CUDA 迁移可行性**（占 50% 价值，未验证不能动工）。

| 验证项 | 方法 | go 标准 |
|---|---|---|
| **CUDA 迁移可行性**（最关键）| 选 3 个典型 CUDA 算子（elementwise / reduction / matmul 各一），用"LLM 迁移 + 规则辅助"尝试到 AscendC | 测出准确率分档：全自动通过率 / 需人工修正比例 / 完全失败比例 |
| cann_compile 环境 | 在开发机/30卡池验证 cann_compile 可跑 | 能编译一个 AscendC kernel |
| numpy-kernel diff 协议 | 定 kernel 输出与 numpy 基线的对比格式 + 容差 | 能算 abs_err/rel_err/cos_sim |
| cannbot-skills 检索质量 | 验证阶段感知加载是否取到对的 skill | Phase2 prompt 实际加载 ascendc-tiling-design |

**CUDA 准确率分档决定路径**（Spike 0 产出）：
- 全自动通过率 ≥60% → P0 做 CUDA 全自动前端
- 全自动 30-60%、人工修正后 ≥80% → P0 做 CUDA 半自动（LLM 草稿 + 人工修正工作流）
- 全自动 <30%、人工修正也难 → CUDA 降级为"仅辅助"，主推 Triton + 新算子，CUDA 标记为"需人工"

### P0（核心，6-9 周）——双轨选择性迁移闭环

目标：含 Triton + CUDA 自定义算子的客户模型，跑完 阶段1→4 闭环（单算子为主，2-3 个并行）。

| 模块 | LOC | 说明 |
|---|---|---|
| **cannbot-skills 集成** | ~200-400 | git submodule + PromptBuilder Layer 6 阶段感知加载 |
| **阶段机 + checkpoint** | ~600-900 | LangGraph StateGraph，单算子崩溃恢复 |
| **Triton 迁移前端** | ~300-500 | 胶水层，复用 cannbot triton 5-skill 链 |
| **CUDA 迁移前端** | ~1500-3500 | **按 Spike 0 结果定范围**：全自动 / 半自动 / 仅辅助。SMEM↔UB、tile 推断、异步流水线映射 |
| **性能分析 + 耗时占比 + 决策** | ~600-1000 | 跑模型 profiling，算子级耗时，迁移难度预估，决策可视化 |
| **轻量 NPU 资源池** | ~800-1200 | 单租户多任务：卡池状态、排队、共享/独占、失败重试 |
| **精度/性能验证（共享后端）** | ~400-600 | vs 原算子 + numpy 基线 + 迁移前后端到端 |
| **合计 P0** | **~4400-8100** | 单人 6-9 周（CUDA 前端是大头，Spike 0 决定）|

**P0 验收**：一个含 3-5 个 Triton + CUDA 混合算子的模型，profiling 出耗时占比 → 勾选 top 3-5 → 并行迁移（6-10 卡）→ 精度性能验证通过。双前端都跑通即验收。

### P1（扩展，6-10 周）——批量 + 闭环

| 模块 | LOC | 说明 |
|---|---|---|
| **批量迁移控制器** | ~800-1400 | 1-10 算子并行，独立 checkpoint，失败分类，部分恢复 |
| **闭环修复控制器** | ~300-500 | review→fix→re-review→stop，有界循环 |
| **CUDA 前端深化**（若 Spike 0 显示半自动）| ~1000-2000 | 提升准确率，扩展算子类（matmul/attention/conv）|
| **CUTLASS 迁移**（可选）| ~1500-3000 | 复用 CUDA 前端 + CUTLASS 特化 |
| **合计 P1** | **~3600-7200** | 单人 6-10 周 |

### 明确不做（自用低价值）

| 模块 | 原因 |
|---|---|
| 多租户隔离/计费/配额 | 单团队自用 |
| 结构化审计签名 | 自用不需合规审计 |
| CI/CD PR 自动化 | 自用本地开发 |
| SaaS 多租户控制台 | 不商业化 |
| 统一编译器 IR | 研究级，超范围 |

## 第五节：最大风险——CUDA 迁移（已前置）

**事实**：cannbot-skills 的 `cuda2ascend-simt` 是**空桩**（Ascend 950 PR only，文件缺失）。华为都没把 CUDA→AscendC 迁移沉淀成 skill。

**5:5 比例下的含义**：CUDA 占 50%，**无法像"Triton 为主"那样推迟 CUDA**。Spike 0 必须先验证，否则 P0 投入 6-9 周后可能发现 CUDA 路径不可行，50% 价值落空。

**Spike 0 的 CUDA 验证设计**（关键）：
1. 选 3 个代表算子：elementwise（Add/ReLU）、reduction（Sum/Max）、matmul（GEMM）
2. 每个用"LLM（Claude Code + cannbot ascendc-api-best-practices）+ 轻量规则翻译器"尝试迁移
3. 讋录：全自动一次通过率、需几轮人工修正、完全失败比例、典型错误类型
4. 产出"CUDA 自动化程度档位"，直接决定 P0 的 CUDA 前端范围和 LOC

**如果 Spike 0 显示 CUDA 完全不可行**（最坏情况）：
- 产品价值从"覆盖 100% 客户算子"降到"覆盖 Triton + 新算子（约 50-60%）"
- CUDA 算子标记为"需人工迁移，引擎仅辅助"
- 这仍是可用产品，但定位要诚实下调，工期缩短（砍 CUDA 前端，P0 降到 4-6 周）

## 第六节：30 卡 NPU 池的简化设计

场景是**单租户多任务**（一个团队、30 张自己的卡），不是多租户 SaaS：

| 商业版多租户调度（不做） | 自用版单租户调度（做） |
|---|---|
| 租户隔离、计费、配额、SLA | ❌ 不需要 |
| — | ✅ 卡池状态表（空闲/占用）|
| — | ✅ 任务排队（FIFO + 优先级）|
| — | ✅ 共享/独占切换（profiling 独占，编译共享）|
| — | ✅ 失败检测（OOM/ECC/hang）+ 重试 |
| — | ✅ 结果归档（build hash + timestamp + 基线对比）|

**LOC**：~800-1200（商业版多租户要 1200-2000）

**调度模式**：
- 性能分析阶段：客户模型 profiling 需独占若干卡
- 迁移执行阶段：多算子并行，编译不占卡，UT/profiling 占卡

## 第七节：工作量总估（单人，含测试）

| 阶段 | 周数 | 交付 |
|---|---|---|
| **Spike 0**（风险验证，**含 CUDA 可行性**）| **2** | go/no-go：CUDA 自动化档位 + 环境验证 |
| **P0**（双轨选择性迁移闭环）| 6-9 | Triton + CUDA（按档位）闭环跑通 |
| **P1**（批量 + 闭环 + CUDA 深化）| 6-10 | 1-10 并行 + 闭环修复 |
| **合计** | **14-21 周** | 约 3.5-5 个月 |

**对比上一版估（11-17 周）**：上调是因为 5:5 强制 CUDA 前置 + 双轨，CUDA 前端是大头且范围由 Spike 0 决定。

**加速选项**：
- Spike 0 若 CUDA 显示全自动可行（乐观）→ P0 CUDA 前端 LOC 降，总工期 14-16 周

- Spike 0 若 CUDA 不可行 → 砍 CUDA 前端，总工期降到 12-14 周（但产品覆盖下调）
- 找 1 个帮手并行（一人迁移前端、一人 NPU 池+阶段机）→ 压到 10-13 周
