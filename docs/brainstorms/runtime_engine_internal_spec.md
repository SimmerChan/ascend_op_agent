## 执行摘要

**一句话定位**：一个给自己/小团队用的"算子开发运行时引擎"——消费华为官方 cannbot-skills 作为知识层，在其下补一层 Claude Code 结构性缺失的运行时能力（崩溃恢复 + 闭环修复 + 阶段化），让单个算子从"人盯着的 pair programming"变成"半自动、可恢复、闭环验证的开发流程"。

**核心判断**：值得做，但范围要砍。商业版要做的 NPU 调度/审计签名/批量/CI 这 4 个模块，自用场景价值低，**全部砍掉或列为可选**。MVP 聚焦 3 件事：阶段机+checkpoint、cannbot-skills 集成、闭环修复。

**投入**：单人 **4-6 周**（商业版估 8.5 周，自用版砍 ~40%）。**回报**：把单算子从"崩溃重来、手动查日志、反复贴 review"变成"崩溃自动恢复、自动闭环修复"，预估单算子开发周期缩短 30-50%。

**临界点（什么情况不值得做）**：如果你一个月只做 1-2 个简单 elementwise 算子，直接用 Claude Code + cannbot-skills 更划算，本工具的开发投入收不回来。值得做的门槛见第三节。

## 第一节：目标用户与场景

### 1.1 用户画像（自己 / 小团队）

| 维度 | 设定 |
|---|---|
| 角色 | 算子开发工程师（你自己 + 可能 1-3 个同事）|
| 硬件 | 本地或远程 1-2 张昇腾卡（910B / 910C / 950）|
| CANN 环境 | 已配好（ASCEND_HOME_PATH、cann_compile、msop 可用）|
| 编码习惯 | 已用 Claude Code 或 Cursor 日常编码 |
| 算子量级 | 中低频，每月数个到十几个算子 |
| 痛点 | 不是"写不出代码"，而是"流程断裂"（崩溃重来、结果对不上、改了又改）|

> ⚠️ **假设标注**：以上是"个人/小团队、1-2 卡、单算子开发+偶尔迁移"场景。如果你的实际情况不同（如多卡共享、高频批量迁移），第三节和第四节的优先级会变——见文末"场景适配"。

### 1.2 三个典型场景

**场景 A：从零开发新算子**
> "实现一个 RMSNorm，shape [B,S,4096]，float16，支持 910B"

痛点：Claude Code + skills 能生成 kernel 框架，但编译失败后要手动查日志、手动贴回 LLM、手动重试。编译挂在 Phase 4，前面 Phase 0-3 的工作靠对话历史兜底，常丢上下文。

**场景 B：GPU 迁移**
> "把这个 Triton/CUDA 的 FlashAttention 迁移到 AscendC"

痛点：cuda2ascend-simt 是空桩，LLM 靠 pattern match 迁移，30%+ 会错。迁移后精度对不上，要反复对比 numpy 基线，每次都手动跑、手动算误差、手动贴结果。没有闭环。

**场景 C：调优迭代**
> "这个 matmul 慢了 3 倍，帮我调"

痛点：msoprof 跑一次出一堆数据，要手动读、手动判断瓶颈、手动改 tiling、手动重测对比基线。没有"改→测→对比→再改"的闭环，全是手动。

### 1.3 现状痛点清单（用 Claude Code + cannbot-skills 实际遇到的）

| 痛点 | 根因 | 属于哪类缺口 |
|---|---|---|
| 编译崩溃，前面全白干 | 无 checkpoint，JSONL 是对话不是阶段机 | 运行时-阶段机 |
| 改了又改，不知道收敛没 | 无确定性停止条件的闭环 | 运行时-闭环修复 |
| 跨 skill 路径对不上 | 靠约定，路径漂移 | 运行时-数据契约 |
| 精度对不上要手动对比 | 无自动 numpy 基线 + 误差计算 | 运行时-验证 |
| msoprof 结果要手动读 | 无基线对比 | 运行时-profiling 闭环 |
| 迁移后语义错，难定位 | 无结构化 diff 对比 | 运行时-迁移验证 |

**共同特征**：全是运行时缺口，没有一个是"知识不够"（cannbot-skills 知识层够用）。这印证了战略评估——自用工具的价值也只在运行时层。

## 第二节：MVP 边界（自用最大化）

### 2.1 做（MVP 核心，~1300-2200 LOC，4-6 周）

```
                    ┌─────────────────────────────┐
                    │  cannbot-skills（git submodule）│ ← 引入，不重写
                    └──────────────┬──────────────┘
                                   │ Layer 6 阶段感知加载
                    ┌──────────────▼──────────────┐
                    │  AIAgent ReAct 核心（已有）  │ ← 保留
                    └──────────────┬──────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
     ┌────────────────┐  ┌──────────────────┐  ┌─────────────────┐
     │ 阶段机+checkpoint│  │  闭环修复控制器   │  │  NPU 执行封装    │
     │ (崩溃恢复)      │  │ (review→fix→stop) │  │ (单卡, 轻量)     │
     │ ~600-900 LOC    │  │ ~300-500 LOC     │  │ ~200-400 LOC    │
     └────────────────┘  └──────────────────┘  └─────────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  cannbot-skills 集成层        │
                    │  (PromptBuilder L6 改造)      │
                    │  ~200-400 LOC                │
                    └──────────────────────────────┘
```

**模块 1：阶段机 + checkpoint（必做，核心）**
- 把死代码 `src/ascend_op_agent/workflow/` 改造为 StateGraph（LangGraph 或自研，见重构报告）
- SQLite checkpoint：Phase 0-5 状态 + 中间制品（op_info、design_doc、code、compile_result）
- 崩溃后 `invoke(None, config)` 从断点恢复
- **自用价值**：编译常失败（NPU 编译错误率高），这是最高频痛点

**模块 2：cannbot-skills 集成（必做）**
- `git submodule add` 引入 cannbot-skills
- PromptBuilder Layer 6 从"静态占位文本"改为"按当前阶段加载对应 skill 的 Markdown"
- 阶段→skill 映射：Phase0→ops-spec-gen，Phase2→ascendc-tiling-design，Phase4→ascendc-runtime-debug，Phase5→ascendc-ut-develop，等
- **自用价值**：直接享受华为维护的 52 个 skill，不重写知识

**模块 3：闭环修复控制器（必做）**
- 基于 cannbot 的 ascendc-code-review + ascendc-runtime-debug
- 有界循环：review → fix → re-review → diff → 停止条件（max-rounds=5 或 review clean）
- 每轮 transcript 压缩，避免上下文爆炸
- **自用价值**：消除"改了又改不知道收敛没"

**模块 4：NPU 执行封装（必做，轻量版）**
- 单卡封装：cann_compile / msop / msoprof 的统一调用接口
- 结果归档到 checkpoint（带 build hash、timestamp）
- **不做**：多卡调度、设备锁、排队（自用单卡不需要）
- **自用价值**：统一工具调用，结果可回溯

### 2.2 不做（自用低价值，明确砍掉）

| 模块 | 商业版为何做 | 自用版为何砍 |
|---|---|---|
| **NPU 多租户调度器**（~1200-2000 LOC）| 企业多用户共享 NPU | 单人/小团队单卡，无需调度 |
| **结构化审计签名**（~400-700 LOC）| 企业交付需合规审计 | 自用不需要审计签名 |
| **CI/CD 集成**（~500-900 LOC）| 企业 PR 自动化 | 自用本地开发，无 PR 流水线 |
| **批量 200 算子控制器**（~800-1400 LOC）| 企业批量迁移 | 见可选模块——除非真要批量 |

### 2.3 可选模块（按场景启用，不在 MVP）

| 模块 | 何时启用 | LOC |
|---|---|---|
| 批量迁移控制器 | 当你要一次迁移 ≥10 个算子 | ~800-1400 |
| GPU→AscendC 规则翻译器 | 当迁移是主要场景且 LLM 迁移错误率高 | ~2000-4000/类 |
| 多卡调度 | 当团队 ≥3 人共享 ≥2 卡 | ~600-1000（简化版）|

MVP 不做这些，但架构预留接入点（阶段机的 Phase 是 Node，可插拔）。

## 第三节：值不值得自己做（ROI，替代定价逻辑）

### 3.1 投入

| 项 | 成本 |
|---|---|
| MVP 开发（模块 1-4）| 单人 4-6 周 |
| Spike 0 风险验证（cann_compile 环境 / numpy-kernel diff / cannbot-skills 检索）| 1 周 |
| cannbot-skills 集成调试 | 1 周（含在 MVP 内）|
| **合计** | **单人 5-7 周** |

### 3.2 回报（对比 Claude Code + cannbot-skills 纯手工）

| 痛点 | 纯手工耗时 | 有运行时后 | 节省 |
|---|---|---|---|
| Phase4 编译崩溃重来 | 30-60 分钟（重跑 Phase 0-3）| 0（checkpoint 恢复）| 全省 |
| 闭环修复一轮 | 15-30 分钟（手动 review/fix/贴结果）| 2-5 分钟（自动循环）| 80% |
| 精度对比 | 20-40 分钟（手动跑 numpy/算误差）| 3-5 分钟（自动基线）| 85% |
| msoprof 读数+对比 | 20-30 分钟 | 5 分钟（自动基线 diff）| 75% |

**单算子预估**：从 ~4-8 小时（含调试来回）缩短到 ~2-4 小时，**省 30-50%**。

### 3.3 回本门槛（关键判断）

**投入 5-7 周开发，换每个算子省 2-4 小时。回本点 ≈ 70-140 个算子。**

- 如果你预期未来 6-12 个月会做 **≥30 个算子**：值得做（尤其编译崩溃高频时）
- 如果每月只做 **1-2 个简单算子**：不值得，直接用 Claude Code + cannbot-skills，省下的 5-7 周做别的
- 如果你做的是**高复杂度算子**（matmul/attention/conv，调试来回多）：门槛降低，≥15 个就值得

### 3.4 不值得做的明确信号

如果以下任一为真，建议放弃自建，直接用 Claude Code + cannbot-skills：
- 单月算子产量 < 3 个
- 算子类型集中且简单（纯 elementwise）
- 没有真实 NPU 环境（纯 CPU 模拟，运行时价值打折）
- 已有成熟的内部算子开发脚手架（运行时已被别的东西覆盖）

## 第四节：成功标准（自用版，可衡量）

MVP 完成后，用以下指标自测：

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 崩溃恢复 | Phase4 编译崩溃后，重启能从 Phase4 继续，不丢 Phase 0-3 | 故意 kill 进程，重启验证 |
| 闭环修复 | 一个有 2-3 个编译错误的算子，5 轮内自动收敛或明确报"无法修复" | 跑 3 个测试算子 |
| 阶段感知 skill | Phase2 的 prompt 实际加载 ascendc-tiling-design 内容 | dump system prompt 验证 |
| 单算子周期 | 对比纯 Claude Code，省 ≥30% 时间 | 同一个算子两种方式各跑一次 |
| cannbot-skills 集成 | `git submodule update` 后无需改代码即可用新 skill | submodule 升级测试 |

**MVP 验收算子**（建议）：RMSNorm（elementwise+reduction）、简单 matmul（tiling）、一个 Triton 迁移案例。三个都跑通即验收。

## 附录：场景适配（如果你的情况与假设不同）

本方案按"个人/小团队、1-2 卡、单算子开发+偶尔迁移"写。如果你的场景不同，MVP 优先级调整如下：

| 你的场景 | MVP 调整 |
|---|---|
| **多卡（≥2）+ 多人共享** | 把"多卡调度"从可选提为 MVP（~600-1000 LOC），砍掉别的腾空间 |
| **主要做 GPU 迁移** | 把"GPU→AscendC 规则翻译器"提为 MVP 核心（但这是大头，~2000-4000 LOC/类，可能要扩到 8-10 周）|
| **高频批量迁移（≥10 算子/次）** | 把"批量迁移控制器"提为 MVP（~800-1400 LOC）|
| **纯单算子、偶发** | 进一步砍——只做阶段机+checkpoint + cannbot-skills 集成，砍闭环修复（~800-1300 LOC，3-4 周）|

**场景已确认（2026-06-23）**：
1. **>30 张 NPU 卡**，可共享可独占 → NPU 资源池调度升为 P0（但单租户多任务，砍多租户隔离）
2. **迁移:新开发 = 8:2** → 迁移流水线升为 P0 核心；Triton 优先（cannbot 成熟），CUDA 单独 spike
3. **批量 1-10 个 + 选择性迁移**（按耗时占比，用户勾选）→ 批量控制器 P0，且需要"性能分析 + 耗时占比 + 决策"环节

**场景确认后的 MVP 落地方案见 [selective_migration_mvp.md](selective_migration_mvp.md)**——本文件第二节 MVP 边界已被其取代（本文件保留作为通用框架参考）。
