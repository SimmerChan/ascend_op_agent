## spike #9 最终状态(链路全通的证据)

### LLM 输出真到 910B(5/5 file)
```
本地 /tmp/e2e_ops_local/op_add/  (markdown 落盘):
  op_kernel.cpp / op_host.cpp / CMakeLists.txt / build.sh(5121B)/ op_kernel.ini
910B /home/hsl/e2e_ops_spike/op_add/  (rsync 后): 同 5 文件
```

### 编译失败根因
```
命令: bash build.sh --soc=ascend910b -j8   (npu_exec.py:235 硬编码 -j{cores})
err:  [ERROR] Unknown option: -j8
```
- **add_example build.sh 认 -j8**(line 101-107 `-j*` case)
- **LLM 写的 build.sh 不认**(没完整复制 add_example 的参数解析逻辑,5121B vs 3291B)
- 即 LLM 在模板基础上"自作主张"改了参数解析,触发新错误

## 真实根因分析(最终)

**不是单点 bug,是 LLM codegen 系统性偏差**:

- ✅ GLM-5.2 / Minimax 都能产完整工程结构(5 文件 + 合理 AscendC 代码)
- ✅ cannbot skill(add_example 内联)提供正确构建模板
- ❌ **LLM 单次写不对构建文件**:漏环境变量 / 加多余参数 / 参数解析不全 / 模板版本偏差
- 每次修一层,下一层偏差浮现 —— prompt 工程无法收敛的长尾

**正确收敛路径 = compile fix_loop**(graph 已设计,未接通):
```
compile 失败 → stderr 反馈 → LLM 修 build.sh/CMakeLists → 重编译 → 多轮收敛
```
当前 spike 的 review_fix 是 codegen 后**静态 review**(不接 compile 结果),fix_loop 未接通 —— 这是 U2/U3 的 graph 工作。
